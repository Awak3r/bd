# Лабораторная работа № 2
## Разработка SQL-запросов и аналитических сценариев для реляционной базы данных

*(источник: PDF из группы «БД 2026/27», сообщение от 21.10.2026)*

## Общая постановка задачи
В ЛР №1 была разработана реляционная БД для заданной предметной области. Теперь нужно реализовать набор SQL-сценариев, обеспечивающих получение операционной информации и аналитических показателей из существующей БД.

Все задания выполняются **на собственной модели данных из ЛР №1**. Запрещено:
- менять предметную область;
- использовать демонстрационные БД;
- создавать отдельную упрощённую схему специально для запросов.

Допускается расширение модели дополнительными атрибутами и связями, если это необходимо для аналитических сценариев. Изменения должны быть обоснованы и выполняться с сохранением ранее созданных данных.

## Часть 1. Подготовка данных и DML

### 1.1. Содержательный набор данных
Дополнить базу тестовыми записями так, чтобы были и типовые, и нетривиальные ситуации:

- ≥ 100 записей суммарно в содержательных таблицах, из них ≥ 30 в одной из основных операционных таблиц;
- ≥ 3 различных состояний основного бизнес-процесса (например: создан, выполнен, отменён);
- данные минимум за 3 различных календарных месяца (если домен предполагает учёт событий во времени);
- повторяющиеся операции, связанные с одной сущностью;
- сущности, для которых связанные операции отсутствуют;
- пограничные значения, включая нули и NULL там, где модель допускает.

Данные должны давать содержательные результаты при GROUP BY, фильтрации, JOIN и аналитических вычислениях.

### 1.2. Операции изменения данных
SQL-сценарий, включающий:
1. INSERT — добавление новой сущности и связанных с ней записей.
2. UPDATE — изменение состояния существующей операции.
3. Массовое изменение нескольких записей по содержательному условию.
4. DELETE — удаление записи с учётом ограничений целостности.
5. Демонстрацию отмены изменений с помощью ROLLBACK.

## Часть 2. Получение операционной информации (6 запросов)

### 2.1. Многотабличные запросы (3 запроса с JOIN, каждый — не менее 3 таблиц)
Разные задачи:
- подробная информация об операциях и связанных сущностях;
- выявление объектов, у которых отсутствуют связанные записи;
- перечень объектов, удовлетворяющих нескольким взаимосвязанным условиям.

Как минимум один запрос должен использовать LEFT JOIN и корректно обрабатывать отсутствие связанных данных.

### 2.2. Агрегация и группировка (3 аналитических запроса с GROUP BY)
1. Расчёт количественных показателей по группам.
2. Расчёт суммарных/средних показателей с фильтрацией групп через HAVING.
3. Сравнение показателей между категориями объектов или временными периодами.

Нужно ≥ 3 агрегатных функций из COUNT, SUM, AVG, MIN, MAX. Простое получение количества строк таблицей не считается аналитической задачей.

## Часть 3. Подзапросы и поиск нетривиальных ситуаций (4 запроса)

### 3.1. Сравнение с вычисляемым показателем
Найти объекты, чей показатель превышает среднее значение по соответствующей группе (группа задаётся предметной областью — например, той же категорией).

### 3.2. Проверка существования (EXISTS)
Объекты, для которых существует хотя бы одна связанная запись, удовлетворяющая дополнительному условию.

### 3.3. Поиск отсутствующих событий (NOT EXISTS)
Объекты, для которых отсутствует определённое событие/связанная запись. Отсутствие события должно иметь содержательный смысл в домене.

### 3.4. Коррелированный подзапрос
Условие внутреннего запроса зависит от текущей строки внешнего. Должен вычислять индивидуальный показатель или проверять индивидуальное условие для каждой сущности.

## Часть 4. Комплексный аналитический отчёт с CTE (1 запрос)
Полноценный аналитический отчёт в смысле осмысленного результата выполнения запроса, отвечающего на содержательный вопрос «руководителя, аналитика или оператора» системы.

Схема вычислений:
**Исходные данные → Промежуточные показатели → Агрегация → Итоговый отчёт**

Для каждого этапа нужно объяснить вход, преобразования и результат.
