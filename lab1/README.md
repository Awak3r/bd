# Лабораторная работа №1. Проектирование и реализация реляционной базы данных

**Предметная область:** информационная система университета (учебный процесс института).

**Стек:** PostgreSQL.

**Файлы:**
- `schema.sql` — создание структуры БД;
- `data.sql` — тестовые данные;
- `constraints_test.sql` — проверка ограничений целостности;
- `lab1.png` — ER-диаграмма;
- `migration.sql` — изменение структуры по дополнительному требованию (заполняется после выдачи изменения).

## 1. Описание предметной области

Рассматривается учебный процесс института (в качестве основы взят Институт №8 МАИ). В институте есть **кафедры** (`departments`); за каждой кафедрой закреплены **преподаватели** (`teachers`) и **дисциплины** (`disciplines`). Обучение ведётся в **студенческих группах** (`student_groups`): группа формируется при наборе на определённый год и включает **студентов** (`students`).

Для конкретной группы в конкретном учебном году и семестре по дисциплине организуется **курс** (`courses`): дисциплина читается группе определённым преподавателем. Таким образом, курс — связь «дисциплина + группа + преподаватель + семестр + учебный год».

Основные сущности и связи:

| Сущность | Смысл | Связи |
|---|---|---|
| departments | кафедра | 1:M → teachers, 1:M → disciplines |
| teachers | преподаватель | M:1 → departments |
| disciplines | дисциплина | M:1 → departments |
| student_groups | студенческая группа | 1:M → students, 1:M → courses |
| students | студент | M:1 → student_groups |
| courses | курс (преподавание дисциплины группе) | M:1 → disciplines, student_groups, teachers |

## 2. Основные проектные решения

### 2.1. Ключи

Все таблицы имеют суррогатный первичный ключ `id bigint`. Обоснование: естественные ключи либо громоздкие (ФИО + дата рождения), либо изменяемые (email, название кафедры), поэтому в качестве PK они не подходят. Email и названия уникальны, но это отдельные ограничения UNIQUE, а не первичные ключи.

### 2.2. Типы данных PostgreSQL

| Атрибут | Тип | Обоснование |
|---|---|---|
| `id`, `*_id` | `bigint` | суррогатные ключи; запас по размеру |
| `name`, ФИО, `email` | `varchar(n)` | ограничение длины на уровне БД; `middle_name` допускает NULL (отчество может отсутствовать) |
| `birth_date` | `date` | только дата, без времени |
| `credits`, `course_number`, `semester`, `academic_year`, `admission_year` | `smallint` | значения малы (2 байта), диапазона достаточно |

### 2.3. Ограничения целостности

**UNIQUE (5 + 1 составное):**
- `uq_departments_name` — название кафедры уникально;
- `uq_departments_short_name` — краткое имя кафедры уникально;
- `uq_teachers_email` — email преподавателя уникален (используется как логин);
- `uq_students_email` — email студента уникален;
- `uq_groups_name` — название группы уникально;
- `uq_courses_discipline_group_semester_year` — **составное**: одна и та же дисциплина не может быть прочитана одной группе дважды в одном семестре и учебном году.

**CHECK (5):**
- `chk_disciplines_credits_positive` — зачётные единицы положительны (`credits > 0`);
- `chk_groups_course_number` — курс обучения от 1 до 6;
- `chk_groups_admission_year` — год набора в разумных пределах (2000–2100);
- `chk_courses_semester` — семестр от 1 до 12;
- `chk_courses_academic_year` — учебный год позже 2000.

**NOT NULL** — для всех обязательных атрибутов (id, внешние ключи, ФИО, email, даты и т.д.). Необязателен только `middle_name` — отчество может отсутствовать.

### 2.4. Правила ON DELETE

Выбор правила соответствует семантике предметной области:

| Внешний ключ | Правило | Обоснование |
|---|---|---|
| teachers → departments | RESTRICT | нельзя удалить кафедру, пока на ней работают преподаватели |
| disciplines → departments | RESTRICT | нельзя удалить кафедру, пока за ней закреплены дисциплины |
| students → student_groups | CASCADE | студенты не существуют вне группы: расформирование группы удаляет её состав |
| courses → disciplines | RESTRICT | дисциплину нельзя удалить, пока по ней идёт преподавание |
| courses → student_groups | CASCADE | курс существует только для конкретной группы; группы нет — курса нет |
| courses → teachers | RESTRICT | преподавателя нельзя удалить, пока он ведёт курс (SET NULL невозможен: `teacher_id` обязательный) |

Принцип: справочники (кафедры, преподаватели, дисциплины) защищены от «тихой» потери данных (RESTRICT), а зависимые сущности, не имеющие смысла без родителя (студенты и курсы относительно группы), удаляются каскадом.

## 3. Обоснование приведения модели к 3НФ

**1НФ.** Все атрибуты атомарны: нет массивов, списков и повторяющихся групп. ФИО разбито на `first_name`, `last_name`, `middle_name`. Каждый курс — отдельная строка, а не перечисление дисциплин в ячейке.

**2НФ.** Все первичные ключи — простые (суррогатный `id`), поэтому частичные зависимости неключевых атрибутов от части ключа невозможны по построению.

**3НФ.** В каждой таблице неключевые атрибуты зависят только от первичного ключа и не зависят друг от друга:

- `teachers`: все атрибуты (department_id, ФИО, email) описывают преподавателя; названия кафедры вынесены в `departments` — иначе name/short_name кафедры дублировались бы в каждой строке преподавателя (транзитивная зависимость `id → department_id → department.name`);
- `disciplines`: аналогично, атрибуты кафедры живут в `departments`;
- `students`: атрибуты группы (название, год набора) вынесены в `student_groups`;
- `courses`: связь многие-к-многим между дисциплинами и группами «развёрнута» в отдельную сущность с собственными атрибутами (семестр, год, преподаватель); нет зависимостей между semester/academic_year/teacher_id помимо ключа.

### Спорный момент: course_number

Атрибут `course_number` группы формально производен от `admission_year` и текущей даты (номер курса = текущий учебный год − год набора + 1). Это аргумент против 3НФ (транзитивная зависимость через «время»).

Решение оставить его как самостоятельный хранимый атрибут: номер курса меняется со временем **без изменения данных** — группа, набранная в 2024, в течение жизни записи остаётся с `admission_year = 2024`, но её `course_number` растёт (3 → 4 → 5). Хранение номера курса отражает административное состояние группы на момент актуальности данных, а не выводится из других хранимых значений детерминированно. Контроль согласованности (`admission_year`, `course_number`) возложен на приложение; в БД каждый атрибут ограничен CHECK-ом независимо.

Альтернатива (вычисляемое поле или отказ от столбца) усложнила бы частые выборки «расписание для N-курсников», которые в данной предметной области доминируют.

## 4. Проверка ограничений целостности

`constraints_test.sql` содержит 14 операций, которые PostgreSQL обязан отклонить (13 — ошибкой, 14-я демонстрирует CASCADE и откатывается транзакцией):

| № | Операция | Ожидаемое отклонение |
|---|---|---|
| 1–2 | дубликат имени / короткого имени кафедры | `uq_departments_name`, `uq_departments_short_name` |
| 3 | NULL вместо email преподавателя | NOT NULL |
| 4–6 | credits=0, курс 7, год набора 5 | CHECK-ограничения дисциплин и групп |
| 7–8 | семестр 13, учебный год 2000 | CHECK-ограничения курсов |
| 9 | повторный курс (дисциплина+группа+семестр+год) | составной UNIQUE курсов |
| 10–11 | ссылка на несуществующую кафедру / группу | FOREIGN KEY |
| 12 | UPDATE email на чужой | `uq_teachers_email` |
| 13 | DELETE кафедры с преподавателями | RESTRICT |
| 14 | DELETE группы → каскадное удаление студентов (в транзакции с ROLLBACK) | CASCADE |

Запуск:

```bash
psql -d lab1 -v ON_ERROR_STOP=1 -f schema.sql -f data.sql
psql -d lab1 -f constraints_test.sql   # ON_ERROR_STOP НЕ нужен: ошибки — ожидаемый результат
```

Каждая операция из файла должна завершиться сообщением об ошибке, называющим конкретное ограничение. Это и есть демонстрация работы ограничений целостности.
