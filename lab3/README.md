# ЛР3. Аналитические запросы и представления в PostgreSQL

Предметная область — деканат: факультетские кафедры, дисциплины, учебные группы,
студенты, курсы (закрепление дисциплины за группой и преподавателем) и попытки
сдачи дисциплин (таблица `grades`).

## Порядок применения

Скрипты выполняются поверх схемы и данных ЛР1/ЛР2:

```
lab1/schema.sql
lab1/data.sql
lab2/migrations/01_grades_with_data.up.sql
lab3/01_ranking.sql
lab3/02_sequence.sql
lab3/03_contribution.sql
lab3/04_views.sql
lab3/05_matview.sql
```

Пример запуска из корня репозитория на чистой базе PostgreSQL 17:

```bash
createdb lab3
psql -X -d lab3 -v ON_ERROR_STOP=1 \
  -f lab1/schema.sql \
  -f lab1/data.sql \
  -f lab2/migrations/01_grades_with_data.up.sql \
  -f lab3/01_ranking.sql \
  -f lab3/02_sequence.sql \
  -f lab3/03_contribution.sql \
  -f lab3/04_views.sql \
  -f lab3/05_matview.sql
```

На подготовленной базе достаточно запустить SQL-файлы `lab3/`. Их можно
запускать повторно: запросы только читают данные, представления пересоздаются,
а демонстрационные изменения откатываются. Ожидаемый отказ `WITH CHECK OPTION`
проверяется отдельной командой в п. 2.3, чтобы не прерывать общий запуск.

## Часть 1. Аналитические запросы

### 1.1. Сравнение объектов внутри групп — `01_ranking.sql`

Рейтинг студентов внутри учебной группы по среднему баллу.

Схема вычислений:

```
grades (оценки попыток)  →  AVG(grade_value) по student_id  →
RANK() OVER (PARTITION BY group_id ORDER BY avg_grade DESC NULLS LAST)  →  место
```

* Равные средние баллы получают одинаковое место — используется `RANK()`
  (а не `ROW_NUMBER()`): следующее место «перепрыгивает» через занятые.
* Студенты без оценок не теряются (`LEFT JOIN grades`) и попадают в результат
  с пустым местом.
* `NULLS LAST` в окне обязателен: в `ORDER BY ... DESC` значение NULL по
  умолчанию идёт первым и сдвинуло бы места студентов с оценками. Места
  определяются по точному среднему; округляется только результат для вывода.

Контрольные данные и ожидаемые результаты:

| Группа | Студент | Средний | Место |
|---|---|---|---|
| М8О-301БВ-24 | Лебедев Д. | 5.00 | 1 |
| М8О-301БВ-24 | Кузнецов А. | 3.75 | 2 |
| М8О-301БВ-24 | Попов И. | 3.67 | 3 |
| М8О-301БВ-24 | Смирнов И. | 3.67 | 3 (равный балл — то же место) |
| М8О-301БВ-24 | Соколов М. | 3.33 | 5 (место 4 пропущено) |
| М8О-301БВ-24 | Сидоров П. | — | пусто (нет оценок) |
| М8О-304БВ-24 | Баранов М. | 5.00 | 1 |
| М8О-304БВ-24 | Орлов В. | 5.00 | 1 |
| М8О-304БВ-24 | Калинин С. | 4.50 | 3 |
| М8О-308БВ-24 … М8О-311БВ-24 | все | — | пусто (у групп нет курсов) |

Фактический результат совпадает с ожидаемым.

### 1.2. Сравнение с предыдущим событием — `02_sequence.sql`

Для каждой попытки сдачи показан интервал в днях от предыдущей попытки того же
студента по той же дисциплине.

```
grades  →  LAG(assigned_on) OVER (
              PARTITION BY student_id, discipline_id
              ORDER BY assigned_on, id)  →  assigned_on - prev  →  дней
```

* Однозначный порядок обеспечивают `assigned_on` и добавленный к нему `id` —
  при совпадении дат порядок всё равно детерминирован.
* У первой попытки предыдущего события нет — `prev_assigned_on` и
  `days_since_prev` равны NULL.

Контрольный случай — студент Алексеев, дисциплина «Стохастическое
моделирование»:

| Попытка | Статус | Назначена | Предыдущая | Дней |
|---|---|---|---|---|
| 1 | failed | 2026-09-11 | — | — |
| 2 | passed | 2026-10-10 | 2026-09-11 | 29 |

Три попытки дают два интервала. Например, у Павла Макарова по «Численным
методам» даты 2026-10-05, 2026-11-06 и 2026-11-20 дают `NULL`, 32 и 14 дней.
Идентификаторы курса и попытки различают события, даже если студент проходил
дисциплину повторно и номера попыток совпали.

### 1.3. Вклад операции в общий показатель — `03_contribution.sql`

Каждая оценённая попытка показана вместе с суммой баллов студента и своей
долей в этой сумме. Попытки без выставленного балла в отчёт не входят.

```
grades  →  SUM(grade_value) OVER (PARTITION BY student_id)  →  student_total
        →  grade_value / student_total * 100                 →  share_pct
```

Контрольный случай — студент Алексеев (сумма 10):

| Дисциплина | Попытка | Балл | Сумма | Доля, % |
|---|---|---|---|---|
| Программирование | 1 | 5 | 10 | 50.0 |
| Стохастическое моделирование | 1 | 2 | 10 | 20.0 |
| Стохастическое моделирование | 2 | 3 | 10 | 30.0 |

До округления сумма долей равна 100 %. Округлённые значения могут дать другой
итог: у Георгия Богданова три доли по 33,3 % дают 99,9 %.

## Часть 2. Представления — `04_views.sql`

### 2.1. Операционное представление `v_gradebook`

Единая ведомость: одна строка = одна попытка сдачи с полным контекстом
(студент, группа, дисциплина, преподаватель, семестр, учебный год, попытка,
статус, оценка, даты). Объединяет шесть таблиц: `grades`, `students`,
`student_groups`, `courses`, `disciplines`, `teachers`.

Влияние изменений исходных данных демонстрируется в транзакции:

```
BEGIN;
SELECT ... WHERE grade_id = 100001;         -- grade_value = 5
UPDATE grades SET grade_value = 3 WHERE id = 100001;
SELECT ... WHERE grade_id = 100001;         -- grade_value = 3 (изменение видно сразу)
ROLLBACK;
SELECT ... WHERE grade_id = 100001;         -- grade_value = 5 (после отката)
```

Обычное представление не хранит данные — оно всегда отражает текущее состояние
базовых таблиц.

### 2.2. Аналитическое представление `v_student_avg_grade`

Средний балл и число оценённых попыток по каждому студенту (на основе
расчёта из 1.1). Сначала отчёт усредняет индивидуальные средние баллы **всех
студентов группы с оценками**. Каждый студент имеет одинаковый вес независимо
от числа попыток. Затем отчёт отбирает студентов со средним ниже 3,5 и хотя бы
двумя оценёнными попытками. Отклонение считается до округления.

```
v_student_avg_grade
  → AVG(avg_grade) OVER (PARTITION BY group_id)  →  group_avg
  → WHERE graded_attempts >= 2 AND avg_grade < 3.5
  → avg_grade - group_avg                      →  diff_from_group_avg
```

На исходных данных в отчёт попадают 11 студентов, например:

| Группа | Студент | Попыток | Средний | Средний по группе | Отклонение |
|---|---|---:|---:|---:|---:|
| М8О-301БВ-24 | Соколов М. | 3 | 3.33 | 3.88 | −0.55 |
| М8О-303БВ-24 | Зайцев Р. | 2 | 2.50 | 3.60 | −1.10 |
| М8О-305БВ-24 | Макаров П. | 5 | 2.60 | 3.69 | −1.09 |

### 2.3. Изменяемое представление `v_current_courses` с `WITH CHECK OPTION`

Представление — рабочий интерфейс курсов учебного года 2026 (год контрольных
данных; `WHERE academic_year = 2026`) с `WITH CHECK OPTION`.

В `04_views.sql` семестр курса 1 меняется с 5 на 6. Год остаётся прежним,
поэтому `UPDATE ... RETURNING` показывает обновлённую строку. Затем скрипт
откатывает изменение.

После общего запуска выполни отдельно проверку отказа:

```bash
psql -X -d lab3 -v ON_ERROR_STOP=1 \
  -c 'BEGIN; UPDATE v_current_courses SET academic_year = 2025 WHERE id = 1; ROLLBACK;'
```

Ожидаемый результат — `ERROR: new row violates check option for view
"v_current_courses"`: с годом 2025 курс больше не удовлетворял бы условию
представления. Команда не сохраняет изменений.

## 3. Материализованное представление — `05_matview.sql`

`mv_discipline_stats` хранит число оценённых попыток и средний балл по каждой
дисциплине. `LEFT JOIN` сохраняет дисциплины без оценок: для них число попыток
равно `0`, а средний балл — `NULL`. Например, у «Программирования» 20 оценённых
попыток со средним `4.10`, у «Мехатроники» — 0 и `NULL`.

Деканат может сравнивать успеваемость по дисциплинам, читая готовую сводку
вместо того, чтобы при каждом открытии отчёта соединять таблицы и пересчитывать
показатели. Сводка не меняется при записи новой оценки, пока её не обновят.

## 4. Политика обновления

Допустимая задержка — **до суток**: сводка нужна для ежедневного анализа,
а не для проверки только что выставленных оценок. Политика — выполнять
обновление вручную раз в сутки после окончания занятий, когда сводку читают
реже, потому что обычный `REFRESH` блокирует её чтение на время пересчёта:

```sql
REFRESH MATERIALIZED VIEW mv_discipline_stats;
```
